# Kabin Agent | Copy and Layout Quality Audit

**Date:** 2026-10-08  
**Scope:** All published public bilingual information routes, including their `.en.md` and `.vi.md` sources.  
**Status:** Editorial remediation required. Publication status does **not** equal content approval.

## Decision

**Do not roll out the same design/copy template to more pages.** The current generic radial hero and recurring three-card explanation belong to the scaffolding phase. They need replacement with task- and audience-specific information architecture, visuals, proof boundaries and next actions.

The sample review of `marketplace.en.md`, `solutions--marketing.en.md`, `developers.en.md`, `blog.en.md`, `company.en.md` and `legal--terms.en.md` found the same `Positioning → Content pillars (three) → Related navigation → Contact → Corporate identity → Editorial constraints` outline. This is **source structure**, not finished persuasive or educational content. The HTML examples for Marketplace, Marketing and Developers also repeated the same circular four-node hero visual and broadly interchangeable CTA.

A complete machine inventory of every HTML/Markdown source pair is generated by `scripts/audit-copy.mjs` in GitHub Actions and downloadable as a Markdown/CSV/JSON artifact. The audit only flags structural risks; final copy quality must be reviewed by an editor in both languages.

## Which narrative belongs to which page?

| Page category | Primary framework | What the reader needs | Evidence rules |
|---|---|---|---|
| Homepage / primary landing | AIDA | One clear difference, job-to-be-done, benefit, invitation | No fabricated KPIs or user counts |
| Marketplace overview/category | AIDA + PAS | Why an interchangeable tool list is insufficient, how to evaluate Capacity, what next | Illustrative catalog unless real inventory exists |
| Solutions and role pages | PAS; SSS for scenarios | A precise day-in-the-life friction, consequences, proposed flow, boundary | Clearly label hypothetical personas/scenarios, never fake customer outcomes |
| Developers / APIs / SDK / Manifest | STRINGS educational sequence | Teach the architecture with small example contracts and constraints | Example schemas must say `concept, not production API` |
| Platform deep pages | PAS + explanatory reasoning | Operational failure mode, design tradeoffs, state/evidence model, safe next action | No unverifiable production availability |
| Resources / Blog / Docs | STRINGS | Practical lesson, worked example, useful checklist and further reading | Cite sources for external claims |
| Company / Vision | Authentic story + STRINGS | Why Kabin exists, philosophy, commitment, company identity | No invented founder stories or endorsements |
| Case studies | Evidence-led narrative, not promotional formula | Context, real workflow, attributable approved result, constraints | Without a verified customer case, show editorial holding state, not fabricated success |
| Privacy, Terms, Cookies | FACTUAL / legal review | Actual data collection, hosting, user rights and contact | Do not use marketing persuasion, require legal review |

**Framework definitions:** AIDA = Attention, Interest, Desire, Action. PAS = Problem, Agitate, Solution. SSS = Star, Story, Solution. STRINGS used here = Share, Teach, Reward, Intrigue, Nurture, Generate. Published marketing references vary in whether an additional final Share step is included.

## Acceptance rubric for EACH bilingual page

A page is approved only when an editor can verify all six:

1. **Audience:** Specific decision-maker and search intent. One primary job-to-be-done.
2. **Hook and tension:** A non-generic lead identifying actual friction, not AI hype.
3. **Differentiation:** A reason only Kabin's hybrid Agentic + Routine + Capacity + Memory model addresses this problem.
4. **Proof and example:** A genuine source, verified capability or clearly marked illustrative flow. No hallucinated traction.
5. **Conversion:** One primary next step appropriate to the page and feature availability, with honest microcopy.
6. **Distinct visual storytelling and translation:** The diagram communicates the exact product/task; EN and VI are natural, equivalent and independently edited. Mobile visual QA must pass.

### Editorial review statuses

- `AUDITED_NEEDS_REWRITE`: the page exists but the current outline and reusable visual are below release-quality content.
- `DRAFT_REWRITTEN`: copy has a unique approved framework and useful example; HTML + both Markdown files updated.
- `VISUAL_REVIEW_PENDING`: browser comparison on desktop/mobile not yet approved.
- `APPROVED`: after editorial and visual verification; not inferred from CI alone.

## Distinct page directions for first three prototypes

**Marketplace | AIDA + PAS.** Lead with the friction of owning many AI tools but not knowing which completes a task, then show a *Capacity contract* comparison (inputs, execution environment, approvals, artifacts and evidence), editorial catalog categories, with honest CTA `Explore the capacity model`. Visual: capability shelf or evaluation matrix, not four orbital icons.

**Solutions / Marketing | PAS + SSS (explicitly illustrative).** Show a concrete marketing manager's work from brief to storyboard to captions to review and distribution checkpoint. Challenge: fragmented assets and uncertain publishing status. Proposed flow: Agent coordinates steps, Routine produces assets, human approves external publication. Visual: horizontal production board with stages and receipt states, no invented performance metrics or customer endorsement.

**Developers | STRINGS.** Teach one sample capacity manifest, typed input/output and failure/unknown semantics. Show versioning and integration requirements as *proposed design*, with a trust note that SDK/API are not published. Visual: real-looking documentation surface and callout lines, not generic radial graphic.

## Release process

1. Publish whole-site inventory report from CI (Markdown/CSV/JSON) before rewriting at scale.
2. Rework one narrative/layout family at a time, update EN and VI docs first, then HTML.
3. Compare page-specific headlines and unique value across sibling pages; run static QA and Chromium visual tests.
4. Release only truthful pages. Legal copy requires separate review.
