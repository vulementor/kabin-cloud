# Kabin Agent | Canonical Product Model

**Status: Website editorial authority; product direction, not a claim of released features.**

## One platform, three participating sides

**Kabin Agent is an open AI Agent platform** connecting natural-language user intent with reusable solutions and execution capacities created by the community. Kabin aims to discover, compose, execute, verify and meter work. It is the connecting platform, **not a fourth user segment**.

| Side | Contributes | Receives | Entry |
|---|---|---|---|
| End User | Desired outcome, context, spending limits, approvals | Verified deliverables and clear usage | /use-kabin/ |
| Solution Builder | Problem definition, acceptance criteria, recipe, user experience | Self-used or distributable Outcome Package | /build-solutions/ |
| Capacity Provider | Skill, plugin, SDK, toolkit, model, agent, API, runtime and contract | Distribution and potential metered compensation | /provide-capacity/ |

The same person may be User, Builder and Provider.

## Two discovery perspectives within one economy

1. **Solution / Outcome Exchange:** User-facing catalogue of *jobs that can be completed*, ideally backed by validated versioned ExecutionRecipes.
2. **Capability Exchange:** Builder/provider-facing library of specific capabilities with input/output contracts, runtime, cost, permission, evidence and availability.

A user should choose the **result**, not manually assemble an API stack. A Builder decides the problem and outcome, a Provider supplies executable parts, and Kabin coordinates authorized work.

## Intended operating loop

**Intent → Discover → Negotiate → Compose → Quote and authorize → Execute → Verify → Meter and settle → Learn.**

- OutcomeContract remains inside existing Mission / Work Order authority.
- Prefer valid verified ExecutionRecipes before open-ended planning.
- Kabin Core derives compatibility and owns permissions, identities, execution, effects and evidence. Provider self-claims are insufficient.
- Hybrid Agentic + Routine is an execution strategy: bounded reasoning where needed, deterministic routines where repeatable.
- Verification, especially for uncertain external publish results, must be independent and not become blind retries.
- Marketplace usage billing, Builder/Provider revenue shares, payouts and public commerce are **future product features**, with no published fee split.

## Open ecosystem, controlled trust

Capacities may come from GitHub, SDKs, MCP, A2A, OCI, Python/Node/CLI, managed browser, local/remote workers or APIs. **Found on GitHub does not mean trusted or installable.** The proposed compiler inspects provenance, licensing and runtime, builds candidates in sandbox, runs bounded checks, independently validates evidence and requires admission. Marketplace listing alone never grants invocation authority.
