# Build a capability once. Power many solutions.

A skill, SDK, GitHub toolkit, model or API can contribute to the Kabin ecosystem when its inputs, outputs, rights, runtime and evidence are well defined. Discovery must not mean blindly executing untrusted code.

## Open-source code is abundant. Safe executable contracts are not.

A repository says it detects scenes in an MP4 file. That alone cannot tell a Builder which version works, what GPU it needs, what filesystem it touches, or whether its output is correct. A README is a lead for inspection, not a certificate of trust.

**Differentiation:** A provider supplies bounded execution. Kabin's Core determines whether an invocation is allowed.

## The journey

### 1. Offer a candidate

Identify ownership, provenance, license and the task addressed by a toolkit or service.

### 2. Define a contract

Describe input/output types, resources, side effects, permissions, version and price model.

### 3. Verify in isolation

Sandbox a candidate, probe behavior and preserve independent validation evidence.

### 4. Register deployment

Propose availability, runtime and quotes without assuming listing creates execution authority.

### 5. Participate in usage

Where commerce is implemented, meter verified invocations and settle provider compensation.

## Illustrative example

A scene-detection toolkit accepts an MP4 and returns timestamps. It may satisfy scene analysis in a video solution but cannot be presented as a video renderer. The contract must preserve that gap until an actual rendering Capacity is found.

## Control and authority

1. License, ownership, version and dependency data
2. Input, output and resource contract
3. Permissions, effects, recovery and idempotency
4. Validation evidence, metering and future commercial terms
